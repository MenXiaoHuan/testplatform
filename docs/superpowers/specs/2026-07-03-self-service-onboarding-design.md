# 自助注册与个人空间自动入驻设计

## 背景

当前平台只有登录、获取当前用户、修改昵称、上传头像、登出能力，没有用户自助注册，也没有“新用户入驻”闭环。业务目标是把平台先做成给普通用户使用的自动化测试平台，因此第一版采用最直接的用户入驻模型：

- 用户自助注册
- 注册成功后自动登录
- 系统自动创建个人空间
- 注册用户默认成为自己个人空间的管理员
- 首次进入系统时直接进入个人空间

同时，当前系统还存在两个与这次设计直接相关的问题：

1. 空间审批页存在 MyBatis 映射错误，前端直接暴露数据库异常。
2. 用户没有头像时，部分视图需要兜底默认头像。

## 目标

本次设计目标：

1. 新增用户自助注册能力。
2. 注册成功后自动完成“账号创建 + 个人空间创建 + 管理员角色绑定 + 登录态创建”。
3. 用户名、昵称、空间名称都必须唯一。
4. 注册、审批、头像显示相关错误提示改成面向用户的友好提示。
5. 新注册用户没有头像时，在侧边栏、空间广场、空间审批中都显示默认头像。
6. 修复空间审批列表的后端映射错误，避免底层异常直接暴露到页面。

## 非目标

本次不做以下内容：

- 邀请码注册
- 管理员后台创建用户
- 找回密码
- 邮箱、短信、验证码风控
- 飞书企业组织集成
- 平台级多租户模型

这些能力后续如需扩展，应复用本次设计中沉淀的“用户入驻编排”能力。

## 当前系统现状

### 认证

- 后端 `AuthController` 提供 `/api/auth/public-key`、`/api/auth/login`、`/api/auth/me`、`/api/auth/profile`、`/api/auth/avatar`、`/api/auth/logout`。
- 登录方式为前端用 RSA 公钥加密密码，后端解密后用 bcrypt 校验。
- 登录成功后通过 HttpOnly Cookie 保存 session。

### 用户与空间

- `platform_user` 是平台用户表。
- `space` 表记录空间，带 `owner_user_id`。
- 现有权限模型通过 `space_member` 和空间审批能力管理用户访问空间。
- 当前已有“空间广场”“空间审批”“头像上传”等能力。

### 已知缺陷

- 空间审批列表查询存在 `SpaceAccessRequestProjection` 映射异常。
- 部分用户头像展示位置虽然已有兜底，但要统一成一致策略，并保障新用户注册后展示稳定。

## 方案选择

已确认采用同步注册方案：

`自助注册 -> 自动登录 -> 自动创建个人空间 -> 当前用户成为该空间 ADMIN -> 直接进入个人空间`

不采用异步初始化或拆成两步的原因：

- 当前业务不需要额外复杂度。
- 必须避免出现“用户已创建，但个人空间或角色未创建”的半成品状态。
- 现有 Spring Boot + MyBatis 结构适合通过单事务实现这个闭环。

## 核心业务流

### 用户视角

1. 用户在登录页点击“注册账号”。
2. 填写用户名、昵称、密码、确认密码。
3. 提交成功后，系统自动完成注册并建立登录态。
4. 系统自动为该用户创建个人空间。
5. 用户作为该空间管理员，直接进入 `/spaces/{lastSpaceId}/repos`。

### 系统视角

注册接口在一个数据库事务内完成：

1. 校验用户名唯一。
2. 校验昵称唯一。
3. 解密并校验密码强度。
4. bcrypt 哈希后插入 `platform_user`。
5. 生成个人空间名称：
   - 优先使用 `nickname`
   - 若昵称为空则使用 `username`
6. 校验空间名唯一。
7. 插入 `space`。
8. 插入 `space_member`，角色设为 `ADMIN`。
9. 更新 `platform_user.last_space_id`。
10. 插入 `user_session`。
11. 返回与登录接口一致的当前用户响应。

若任一步失败，整体回滚。

## 数据与约束设计

### 用户唯一性

必须满足：

- `platform_user.username` 全局唯一
- `platform_user.nickname` 全局唯一

当前 `username` 已有唯一约束。需要新增 `nickname` 唯一约束和对应查询能力。

### 空间唯一性

必须满足：

- `space.name` 全局唯一

这样个人空间名默认取昵称或用户名时可以天然避免命名歧义。

### 个人空间命名规则

- 首选：用户昵称
- 备选：用户名

由于昵称和用户名都全局唯一，因此个人空间名默认也唯一。

## 后端设计

### 新接口

新增：

`POST /api/auth/register`

请求体：

```json
{
  "username": "zhangsan",
  "nickname": "张三",
  "encryptedPassword": "..."
}
```

响应体沿用当前登录态结构：

```json
{
  "id": 1,
  "username": "zhangsan",
  "nickname": "张三",
  "avatarObjectKey": null,
  "lastSpaceId": 1001
}
```

同时设置 session cookie，与登录接口行为一致。

### 服务拆分

建议在 `AuthService` 中新增 `register(...)` 方法，负责注册编排。

如实现过程中 `AuthService` 逻辑过重，可抽出 `UserOnboardingService`，负责：

- 创建个人空间
- 绑定默认 ADMIN 角色
- 更新默认空间

第一版允许直接在 `AuthService.register(...)` 中调用 mapper 或 service，优先保证闭环正确。

### 需要扩展的基础能力

后端需要新增或补齐以下能力：

- 根据用户名判断是否已存在
- 根据昵称判断是否已存在
- 插入用户
- 根据空间名判断是否已存在
- 创建空间
- 写空间成员关系
- 更新用户默认空间
- 注册事务测试

### 密码规则

第一版采用简单强校验：

- 长度至少 8 位
- 必须包含字母
- 必须包含数字

不在本次引入特殊字符强制规则，以降低首版门槛。

### 错误码

建议后端返回明确业务错误码，前端按错误码映射中文提示：

- `USERNAME_ALREADY_EXISTS`
- `NICKNAME_ALREADY_EXISTS`
- `SPACE_NAME_ALREADY_EXISTS`
- `INVALID_PASSWORD`
- `REGISTER_FAILED`
- `ACCESS_REQUEST_LIST_FAILED`

控制器层和异常处理层不应将底层 SQL、MyBatis、Java 堆栈原文返回给前端。

## 前端设计

### 登录页与注册页

登录页新增“注册账号”入口。

注册页表单项：

- 用户名
- 昵称
- 密码
- 确认密码

前端本地校验：

- 必填校验
- 密码长度和格式校验
- 两次密码一致校验

### 注册成功后的跳转

注册成功后：

1. 保存后端返回的用户状态到 `authStore`
2. 刷新或初始化 `spaceStore`
3. 直接跳转到 `/spaces/{lastSpaceId}/repos`

不回登录页，不要求用户重新输入密码。

### 错误提示文案

注册相关友好提示：

- 用户名重复：`该用户名已被使用，请换一个`
- 昵称重复：`该昵称已被使用，请换一个`
- 空间名冲突：`系统为你生成个人空间时发现名称冲突，请修改昵称后重试`
- 密码不符合规则：`密码至少 8 位，且需包含字母和数字`
- 两次密码不一致：`两次输入的密码不一致`
- 注册失败兜底：`注册失败，请稍后重试`

审批页相关友好提示：

- 审批列表加载失败：`审批列表加载失败，请刷新后重试`

### 默认头像策略

新用户注册后默认没有头像，前端统一使用默认头像资源兜底。

需要统一的展示位：

- 侧边栏用户卡片
- 空间广场 Owner 头像
- 空间审批申请人头像

统一规则：

- `avatarUrl == null` 时显示默认头像
- 图片加载失败时显示默认头像
- 用户后续上传新头像后，组件应能从默认头像状态恢复

## 审批页报错修复设计

当前空间审批页存在 `SpaceAccessRequestProjection` 映射异常，应作为本次改动的前置修复项。

处理策略：

1. 修正审批列表查询的 MyBatis 映射方式，避免 record/setter 反射异常。
2. 为审批列表 projection/result mapping 增加后端测试。
3. 控制器或统一异常处理将加载失败转成业务错误码，不返回底层异常原文。
4. 前端使用统一中文提示，不再显示底层数据库错误。

## 实施顺序

建议按以下顺序落地：

1. 修复空间审批列表 mapper 报错
2. 统一默认头像兜底
3. 实现后端注册事务
4. 实现前端注册页与自动登录跳转
5. 接通注册后的空间初始化与路由跳转
6. 收口各种边界错误提示

## 测试策略

### 后端

重点测试：

1. 注册成功事务：
   - 创建用户
   - 创建个人空间
   - 创建 ADMIN 成员关系
   - 写入 `last_space_id`
   - 创建 session

2. 唯一性失败：
   - 用户名重复
   - 昵称重复
   - 空间名冲突
   - 并确认事务回滚

3. 审批列表查询：
   - 用户名
   - 昵称
   - 头像字段
   - 状态字段
   - 不再出现映射异常

4. 头像空值：
   - 注册用户头像为空
   - `/auth/me` 返回空头像不影响注册和登录闭环

### 前端

重点测试：

1. 注册表单校验
2. 注册成功自动登录并跳转个人空间
3. 默认头像展示与加载失败回退
4. 错误码映射成友好中文提示

### 手工验收链路

必须跑通以下链路：

`新用户注册 -> 自动进入个人空间 -> 个人空间可正常操作 -> 侧边栏/广场/审批头像展示正常 -> 空间审批页无底层异常`

## 风险与注意事项

1. 昵称唯一后，用户后续修改昵称也必须做唯一校验。
2. 空间名全局唯一后，普通空间创建、编辑也要复用这条约束与友好提示。
3. 注册事务中如果直接使用现有 space service，需要确认不会误触发与当前登录态耦合的逻辑。
4. 审批页 mapper 修复要优先落地，否则用户仍可能在新注册后浏览审批页时看到系统内部错误。

## 结论

第一版以“自助注册 + 自动个人空间入驻”为核心，保持系统对普通用户可直接使用，同时不提前引入邀请码、后台用户管理、企业集成等复杂能力。实现重点是：

- 用单事务保证入驻闭环完整
- 用唯一性约束保证命名规则稳定
- 用统一默认头像和友好错误提示保障体验
- 先修掉空间审批页已有的后端异常
